# Orca 0.31.0

Performance release. No renderer or styling changes: the parser got faster where it was
accidentally quadratic, the streaming session got useful where it previously was not, and
the whole thing is now guarded by benchmarks that run on every push.

## Highlights

- **Definition-list scanning is linear.** `extractDefinitionLists()` probed every line for a
  possible list start, and each probe walked forward to the end of the current paragraph. On a
  document that is one long paragraph — most documents — that is O(n²). Definition lines are
  now located in one pass and a list is only attempted on the single line that could open one.
  8 000 lines: **4 358 ms → 2 ms**. A full parse of a 4 000-line document: **450 ms → 83 ms**.
- **Streaming understands code fences.** The incremental session cut segments at blank lines
  only, so a stream sitting inside a ``` block could not freeze anything and re-parsed the
  growing block on every token. Segments are now also cut at completed top-level structures:
  text before an open fence freezes while the block streams, and the block freezes the moment
  its closing line arrives. An open fence tail is rebuilt directly instead of being re-parsed,
  after a one-time equivalence check against the delegate.
  A streamed assistant answer (prose, a 60-line fence, a list, a second fence, 16-character
  chunks) went from **0.66× to 12× faster** than re-parsing every prefix on code-heavy answers,
  and now feeds the parser **1.7 % of the characters** a full re-parse does.
- **The inline scanner has a depth guard.** Resolving link openers backtracks over every
  unmatched `[` in a block, which is quadratic: `[` × 12 800 took 2.5 s, `[` × 25 600 looked
  like a deadlock, and `![` × 25 600 was far worse. Blocks above `maxInlineBracketDepth`
  (default 512) are kept verbatim as plain text paragraphs instead of being scanned.
  `[` × 25 600: **hang → 2 ms**. `[` × 102 400: **5 ms**.
- **Benchmarks run in CI.** The new `orca-benchmarks` module measures parsing, guarding, and
  streaming and fails the build on scaling regressions. Checks are ratio based (does 4× input
  cost more than 7× time?), so the same limits hold on a laptop and on a shared runner.

## Correctness fixes found while doing the above

The streaming rewrite is covered by a differential fuzzer that streams thousands of generated
documents character by character and compares every prefix against a full parse. It found
three pre-existing ways a streamed prefix could differ from a full parse:

- A ```` ``` ```` line with backticks in its info string is not a fence opener (CommonMark), but
  the segment scanner treated it as one, inverting its fence state for the rest of the document.
- A list starting part way into a segment did not mark that segment continuable, so a cut could
  be placed between two items of the same list.
- `<details>` and `$$` extraction run over the raw source before the parser and do not share the
  scanner's view of fenced code. Cuts are now refused wherever either pre-pass would still be
  mid-region.

## API

```kotlin
OrcaMarkdownParser(
    // …
    maxInlineBracketDepth = 512, // unmatched `[` per block before it is kept as plain text
)

// New diagnostic when a block is kept as plain text:
OrcaParseWarning.InlineBracketLimitExceeded(
    maxInlineBracketDepth = 512,
    exceededDepth = 25_600,
    guardedBlocks = 1,
)

// New streaming counter:
session.stats.codeFenceFastPaths // updates whose tail was a rebuilt growing code fence
```

`OrcaIncrementalParseStats` gained a field and `OrcaMarkdownParser` gained a trailing
parameter; both are source compatible, neither is binary compatible with 0.30.0.

## Running the benchmarks

```bash
./gradlew :orca-benchmarks:run --args="--check"   # what CI runs
./gradlew :orca-benchmarks:run --args="--quick"   # shorter local run
```

## Measurements

Taken on a warm JVM, minimum of several runs, `--quick` budgets.

| case | 0.30.0 | 0.31.0 |
|---|---:|---:|
| `extractDefinitionLists`, 8 000-line paragraph | 4 358 ms | 2 ms |
| full parse, 4 000-line paragraph | 450 ms | 83 ms |
| `[` × 25 600 | minutes | 2 ms |
| streamed answer, prose-heavy | 6.6× vs full re-parse | 8.5× |
| streamed answer, code-heavy | 0.66× vs full re-parse | 12× |
| streamed answer, delegate characters | 254 366 | 6 290 |
